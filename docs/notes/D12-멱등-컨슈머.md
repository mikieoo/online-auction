# D12 — 멱등 컨슈머 (Idempotent Consumer)

## 왜 필요한가

D11 Outbox 패턴은 at-least-once 전달을 보장한다. 같은 이벤트가 두 번 이상 올 수 있다.

중복 수신 경로:
1. **Outbox 폴러 재전송** — Kafka 전송 후 markPublished() 전에 앱이 죽으면 재전송
2. **Kafka 리밸런싱** — 오프셋 커밋 전 파티션 이동 시 메시지 재수신
3. **컨슈머 재시도** — 처리 실패 후 재시도 시 부분 처리된 이벤트 재수신

## 적용 전 멱등성 현황

| 컨슈머 | 멱등 여부 | 근거 |
|---|---|---|
| payment `AuctionWonEventConsumer` | O | idempotencyKey UNIQUE 제약 |
| auction `handlePaymentCompleted` | O | completeAuction() 상태 체크 |
| auction `handlePaymentFailed` | **X** | 방어 없음 — reassignWinner 중복 호출 위험 |

## 구현 방식: processed_event 테이블

이벤트 처리 완료를 DB에 기록하고, 같은 eventId가 다시 오면 건너뛴다.
비즈니스 로직과 같은 트랜잭션에서 INSERT → 원자적 보장.

### 왜 DB 테이블인가 (Redis가 아닌 이유)

- 비즈니스 DB와 같은 트랜잭션에서 INSERT해야 원자적
- Redis에 쓰면 DB 커밋 후 Redis 쓰기 전에 죽으면 중복 처리 가능
- 추가 인프라 불필요

### IdempotentHandler 핵심 구조

```
processOnce(eventId, handlerName, Runnable action)
├─ existsById(eventId) → true이면 false 반환 (skip)
├─ saveAndFlush(ProcessedEvent) → UNIQUE 위반 시 false 반환 (동시 처리)
└─ action.run() → 비즈니스 로직 실행 (같은 트랜잭션에 합류)
```

### handlePaymentFailed 흐름 (가장 복잡한 케이스)

```
1. isAlreadyProcessed(eventId) → true? → 건너뜀 (gRPC 호출도 안 함)
2. gRPC: bidGrpcClient.reassignWinner() (트랜잭션 밖)
3. processOnce(eventId, "PaymentFailed", () -> {
       settlementService.reassignWinner() 또는 failAfterAllBiddersExhausted()
   })
   └─ 한 트랜잭션: processed_event INSERT + 경매 상태 변경 + outbox 기록
```

## 동시 처리 시나리오

두 인스턴스가 같은 이벤트를 동시에 받으면:
- 둘 다 사전 체크 통과 (아직 커밋 전)
- 둘 다 gRPC 호출 (외부 호출은 중복 가능)
- processOnce()에서 한쪽만 INSERT 성공, 다른 쪽은 UNIQUE 위반 → skip
- **결론: DB 쓰기는 정확히 한 번만 실행됨**

gRPC 중복 호출 방어는 bid-service 쪽에서 해야 한다 (이미 DISQUALIFIED인 입찰자 무시).

## 면접 포인트

1. **at-least-once + 멱등 컨슈머 = effectively exactly-once** — 브로커가 중복 전달하더라도 컨슈머가 흡수
2. **왜 eventId 기반인가** — 모든 이벤트에 UUID eventId가 있어 범용적. 비즈니스 키(auctionId) 기반은 같은 경매의 다른 이벤트를 구분 못함
3. **processed_event 테이블 관리** — Kafka retention(7일)보다 긴 기간만 유지하면 됨. 배치 삭제 또는 파티셔닝
4. **자연 멱등으로 충분한 경우** — 단순 상태 전이(CLOSED→COMPLETED)는 상태 체크만으로 충분. 복잡한 사이드이펙트(gRPC+상태변경+outbox)가 있으면 처리 기록이 안전
