## 1. Gradle 멀티 모듈 프로젝트

### 왜 멀티 모듈인가

MSA에서 각 서비스는 독립적으로 빌드·배포되어야 한다. 모노리포(하나의 저장소) 안에서 Gradle 멀티 모듈로 구성하면:
- 공유 코드(이벤트 DTO)를 `common` 모듈로 분리해서 중복 없이 사용 가능
- 각 서비스를 독립적으로 `bootJar`로 빌드 가능
- IDE에서 전체 프로젝트를 한 번에 열 수 있어 개발 편의성 확보

실무에서는 서비스별 별도 저장소(폴리리포)를 쓰기도 하지만, 1인 프로젝트에서는 모노리포가 관리하기 편하다.

### settings.gradle — 모듈 등록

```groovy
rootProject.name = 'auction-platform'

include 'common'
include 'auction-service'
include 'bid-service'
include 'payment-service'
include 'gateway'
```

`include`로 하위 모듈을 등록한다. Gradle은 이 파일을 읽고 각 디렉토리를 서브프로젝트로 인식한다.

### build.gradle (루트) — 전체 설정의 핵심

```groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '3.3.5' apply false
    id 'io.spring.dependency-management' version '1.1.6' apply false
}
```

**`apply false`가 핵심.** 루트에서는 플러그인을 "선언만" 하고 적용하지 않는다. 왜냐하면:
- 루트 프로젝트 자체는 Spring Boot 앱이 아님
- `common` 모듈도 Spring Boot 앱이 아니라 순수 Java 라이브러리
- 실제 Spring Boot 플러그인은 서비스 모듈에만 적용해야 함

```groovy
subprojects {
    apply plugin: 'java'

    java {
        sourceCompatibility = JavaVersion.VERSION_17
        targetCompatibility = JavaVersion.VERSION_17
    }
}
```

모든 하위 모듈에 Java 17을 적용한다. 실제 JDK는 21을 사용하지만 `sourceCompatibility`를 17로 잡아서 Java 17 문법까지만 허용한다. Spring Boot 3의 최소 요구 버전이 17이고, 안정적이라 선택했다.

```groovy
configure(subprojects.findAll { it.name != 'common' }) {
    apply plugin: 'org.springframework.boot'
    apply plugin: 'io.spring.dependency-management'

    dependencyManagement {
        imports {
            mavenBom 'org.springframework.cloud:spring-cloud-dependencies:2023.0.4'
        }
    }

    dependencies {
        implementation project(':common')
        implementation 'org.springframework.boot:spring-boot-starter'
        testImplementation 'org.springframework.boot:spring-boot-starter-test'
    }
}
```

**`common`을 제외한 모든 모듈에만** Spring Boot와 Spring Cloud를 적용한다. `configure(subprojects.findAll { it.name != 'common' })`가 이 필터링을 한다.

- **Spring Cloud BOM(2023.0.4):** Spring Cloud 라이브러리의 버전을 일괄 관리한다. Gateway, Eureka, OpenFeign 등의 버전 충돌을 방지.
- **`implementation project(':common')`:** 모든 서비스가 common 모듈을 의존한다. 이벤트 DTO를 공유하기 위해서.

### common 모듈 — java-library 플러그인

```groovy
plugins {
    id 'java-library'
}

dependencies {
    api 'com.fasterxml.jackson.core:jackson-databind:2.17.2'
}
```

`java-library`는 `java`와 다르다:
- `java`: 실행 가능한 앱을 만들 때
- `java-library`: 다른 모듈이 의존하는 라이브러리를 만들 때

`api`로 jackson-databind를 선언하면, common을 의존하는 모든 서비스에서 별도 선언 없이 Jackson을 사용할 수 있다. (`implementation`과 달리 `api`는 전이적 의존성을 노출한다.)

### 서비스별 build.gradle

```groovy
// auction-service/build.gradle
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
    runtimeOnly 'com.mysql:mysql-connector-j'
}
```

- **starter-web:** REST API를 제공하기 위한 내장 Tomcat + Spring MVC
- **starter-data-jpa:** JPA + Hibernate. 엔티티를 Java 객체로 매핑
- **mysql-connector-j:** MySQL JDBC 드라이버. `runtimeOnly`인 이유는 컴파일 시점에는 필요 없고 실행 시에만 필요하기 때문

```groovy
// gateway/build.gradle
dependencies {
    implementation 'org.springframework.cloud:spring-cloud-starter-gateway'
}
```

Gateway는 **spring-boot-starter-web을 쓰지 않는다.** Spring Cloud Gateway는 Reactive(Netty) 기반이라 서블릿(Tomcat)과 충돌한다. 둘 다 넣으면 기동 시 에러가 난다.

### Gradle Wrapper

```
gradle wrapper --gradle-version 8.10
```

Gradle Wrapper를 사용하면:
- 팀원이 로컬에 Gradle을 설치하지 않아도 `./gradlew build`로 빌드 가능
- 모든 환경에서 **동일한 Gradle 버전**(8.10)을 사용
- CI/CD에서도 별도 설치 없이 빌드

`gradle/wrapper/gradle-wrapper.jar`와 `gradlew` 스크립트가 생성되고, 이것들은 git에 커밋한다.

## 2. 서비스별 DB 스키마

### 왜 서비스별 DB를 분리하는가

MSA의 핵심 원칙: **Database per Service.** 각 서비스가 자기 DB만 접근한다.

- 서비스 간 DB를 공유하면 → 스키마 변경 시 다른 서비스도 영향 → 독립 배포 불가
- DB를 분리하면 → 각 서비스가 독립적으로 스키마를 변경·배포 가능

다른 서비스의 데이터가 필요하면? → REST/gRPC 동기 호출 또는 Kafka 이벤트로 가져온다.

### auction_db 스키마

```sql
CREATE TABLE IF NOT EXISTS product (
    product_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    seller_id BIGINT NOT NULL,
    name VARCHAR(200) NOT NULL,
    description TEXT,
    starting_price DECIMAL(15, 2) NOT NULL,
    created_at DATETIME(6) NOT NULL
);
```

- **BIGINT AUTO_INCREMENT:** PK를 자동 증가 정수로. UUID 대비 인덱스 성능이 좋고 단순함
- **DECIMAL(15, 2):** 금액은 부동소수점(DOUBLE)이 아니라 고정소수점을 써야 한다. `0.1 + 0.2 = 0.30000000000000004` 같은 오차를 방지
- **DATETIME(6):** 마이크로초 정밀도. 경매 시스템에서 시간 정밀도가 중요할 수 있음

```sql
CREATE TABLE IF NOT EXISTS auction (
    ...
    status VARCHAR(20) NOT NULL DEFAULT 'WAITING',
    ...
    version BIGINT NOT NULL DEFAULT 0,
    ...
    INDEX idx_auction_status_end_time (status, end_time),
    INDEX idx_auction_product_id (product_id)
);
```

주요 설계 포인트:
- **status를 VARCHAR(20)으로:** ENUM 대신 문자열을 쓴 이유는 상태가 추가될 때 ALTER TABLE 없이 대응 가능하기 때문
- **version 필드:** JPA의 `@Version` 낙관적 락에 사용. D6에서 구현 예정. 동시에 같은 Auction을 수정하려 하면 먼저 커밋한 쪽이 성공하고 나머지는 `OptimisticLockException` 발생
- **복합 인덱스 (status, end_time):** 스케줄러가 "ACTIVE이면서 end_time이 지난 경매"를 조회할 때 사용. 이 두 컬럼을 묶어서 인덱스를 걸면 풀 스캔 없이 빠르게 찾음
- **reassignment_count:** 차순위 승계 횟수. 결제 실패 시 다음 입찰자에게 기회를 주는데, 최대 3회까지만

```sql
CREATE TABLE IF NOT EXISTS outbox (
    ...
    payload JSON NOT NULL,
    published BOOLEAN NOT NULL DEFAULT FALSE,
    INDEX idx_outbox_published_created_at (published, created_at)
);
```

**Outbox 테이블:** Transactional Outbox 패턴에서 사용. DB 트랜잭션과 이벤트 발행의 원자성을 보장하기 위해, 이벤트를 Kafka로 직접 보내지 않고 먼저 같은 트랜잭션 안에서 outbox 테이블에 저장한다. 별도 폴러가 주기적으로 `published = FALSE`인 행을 읽어 Kafka로 발행. D1에서는 스키마만 만들어 두고, 실제 구현은 D11에서 한다.

### bid_db 스키마

```sql
CREATE TABLE IF NOT EXISTS bid (
    ...
    INDEX idx_bid_auction_amount (auction_id, amount DESC),
    INDEX idx_bid_auction_bidder (auction_id, bidder_id)
);
```

- **(auction_id, amount DESC):** 특정 경매의 최고 입찰을 빠르게 조회. `DESC`로 내림차순 정렬 인덱스를 걸어서 `ORDER BY amount DESC LIMIT 1`이 인덱스만으로 해결됨
- **(auction_id, bidder_id):** 특정 경매에서 특정 사용자의 입찰 이력 조회용

### payment_db 스키마

```sql
CREATE TABLE IF NOT EXISTS payment (
    ...
    idempotency_key VARCHAR(64) NOT NULL,
    UNIQUE KEY uk_payment_idempotency_key (idempotency_key),
    ...
);
```

**멱등성 키(idempotency_key):** `{auctionId}-{winnerId}-{reassignmentCount}` 형태. 같은 키로 두 번 결제 요청이 와도 한 번만 처리되도록 UNIQUE 제약을 건다. Kafka 메시지가 중복 전달될 수 있으므로(at-least-once), 이 키로 중복 결제를 방지한다.

## 3. application.yml 설정

```yaml
server:
  port: 8081

spring:
  datasource:
    url: jdbc:mysql://localhost:3306/auction_db?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Seoul
    username: root
    password: root
  jpa:
    hibernate:
      ddl-auto: none
    open-in-view: false
```

- **ddl-auto: none:** Hibernate가 자동으로 스키마를 생성/수정하지 않는다. 스키마는 SQL 파일로 직접 관리. 프로덕션에서는 반드시 `none`을 써야 데이터 유실을 방지할 수 있다
- **open-in-view: false:** OSIV(Open Session In View)를 끈다. 기본값은 true인데, 이러면 Controller까지 영속성 컨텍스트가 열려 있어서 LazyLoading이 Controller에서도 되지만, DB 커넥션을 오래 점유해서 커넥션 풀 고갈의 원인이 된다. 끄면 Service 계층에서만 JPA 세션이 유지됨
- **allowPublicKeyRetrieval=true:** MySQL 8.0의 caching_sha2_password 인증 플러그인 때문에 필요. 없으면 `Public Key Retrieval is not allowed` 에러 발생

## 4. Docker Compose

```yaml
services:
  mysql:
    image: mysql:8.0
    container_name: auction-mysql
    ports:
      - "3306:3306"
    environment:
      MYSQL_ROOT_PASSWORD: root
    volumes:
      - mysql-data:/var/lib/mysql
      - ./infra/mysql/init:/docker-entrypoint-initdb.d
    command: --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci
```

### MySQL 8.0을 선택한 이유

8.4에서 인증 방식이 바뀌어서 드라이버 호환성 문제가 생길 수 있다. 8.0은 Spring Boot 3.3.5와 안정적으로 동작한다.

### 볼륨 두 개의 역할

1. **`mysql-data:/var/lib/mysql`** — Named Volume. 컨테이너를 재시작해도 데이터가 유지됨. `docker compose down -v`를 하면 이 볼륨이 삭제되면서 데이터가 초기화됨
2. **`./infra/mysql/init:/docker-entrypoint-initdb.d`** — Bind Mount. 로컬의 init 디렉토리를 컨테이너의 `/docker-entrypoint-initdb.d`에 연결. MySQL은 **최초 기동 시에만** 이 디렉토리의 `.sh`와 `.sql` 파일을 알파벳 순서로 실행

### 초기화 스크립트 구조

```
infra/mysql/init/
├── 01-init-databases.sh    ← DB 3개 생성
├── 02-auction-schema.sql   ← USE auction_db; + DDL
├── 03-bid-schema.sql       ← USE bid_db; + DDL
└── 04-payment-schema.sql   ← USE payment_db; + DDL
```

번호 접두사(`01-`, `02-`, ...)로 실행 순서를 보장한다. 01에서 DB를 먼저 만들고, 02-04에서 각 DB에 테이블을 생성한다. 순서가 바뀌면 `USE auction_db;`가 존재하지 않는 DB를 참조해서 에러가 난다.

### MSA에서의 DB 분리 전략

실무에서는 서비스별 독립 MySQL 인스턴스를 쓰는 게 원칙이다. 하지만 로컬에서 MySQL 3개를 띄우면 메모리가 부족하므로, **하나의 인스턴스에 스키마(database)로 분리**하는 전략을 택했다. GKE 배포(D18) 시에는 Cloud SQL 인스턴스로 물리적으로 분리할 예정.

## 5. 공유 이벤트 DTO (common 모듈)

### 이벤트 목록

| 이벤트 | 발행 서비스 | 소비 서비스 | 용도 |
|--------|-----------|-----------|------|
| AuctionStartedEvent | auction | bid | 경매 시작 알림, 입찰 가능 상태 |
| BidPlacedEvent | bid | (CQRS용) | 입찰 발생 기록 |
| AuctionClosedEvent | auction | bid | 경매 마감, 더 이상 입찰 불가 |
| AuctionWonEvent | auction | payment | 낙찰 → 결제 요청 |
| PaymentCompletedEvent | payment | auction | 결제 성공 → 경매 완료 |
| PaymentFailedEvent | payment | auction | 결제 실패 → 차순위 승계 |
| WinnerReassignedEvent | auction | payment | 새 낙찰자 결제 요청 |

### 왜 common 모듈에 넣는가

이벤트 DTO는 발행자와 소비자 양쪽에서 직렬화/역직렬화에 사용한다. 같은 클래스를 공유하지 않으면 양쪽에서 중복 정의해야 하고, 필드가 어긋나면 역직렬화 에러가 발생한다.

**단, common에 넣는 건 이벤트 DTO만.** 엔티티, 리포지토리, 서비스 로직을 공유하면 서비스 간 결합도가 높아져 독립 배포가 어려워진다.

### DTO 구조

```java
public class AuctionWonEvent {
    private String eventId;          // UUID — 이벤트 고유 식별자
    private LocalDateTime occurredAt; // 이벤트 발생 시각
    private Long auctionId;
    private Long winnerId;
    private BigDecimal winningPrice;
    private String idempotencyKey;   // 멱등성 키
    // 기본 생성자 + 전체 필드 생성자 + getter/setter
}
```

- **eventId + occurredAt:** 모든 이벤트에 공통. 이벤트 추적과 중복 감지에 사용
- **기본 생성자 필수:** Jackson이 JSON → 객체 역직렬화할 때 기본 생성자를 호출한 뒤 setter로 값을 주입하기 때문
- **idempotencyKey:** `{auctionId}-{winnerId}-{reassignmentCount}` 형태로 auction-service가 생성. payment-service가 이 키로 중복 결제를 방지

## 면접 대비 포인트

**Q: 왜 멀티 모듈을 선택했나?**
→ 공유 코드(이벤트 DTO)의 중복을 없애면서 각 서비스의 독립 빌드를 유지하기 위해. 1인 프로젝트라 모노리포가 관리 편의성이 높음.

**Q: Database per Service의 단점은?**
→ 조인 불가. 서비스 간 데이터 조회 시 API 호출이 필요해 지연 증가. 분산 트랜잭션 필요 (→ Saga로 해결). 데이터 일관성이 최종 일관성(Eventual Consistency)으로 낮아짐.

**Q: ddl-auto를 none으로 한 이유?**
→ 프로덕션에서 `update`나 `create`를 쓰면 의도치 않은 스키마 변경이 발생할 수 있다. 스키마 변경은 명시적인 SQL 마이그레이션으로 관리하는 게 안전.

**Q: OSIV를 왜 끄는가?**
→ DB 커넥션을 Controller까지 잡고 있으면 커넥션 풀이 빨리 고갈된다. 특히 외부 API 호출이 끼면 응답 대기 중에도 커넥션을 점유. Service 계층 안에서만 영속성 컨텍스트를 사용하는 게 안전.

**Q: Outbox 테이블을 왜 미리 만들었는가?**
→ 나중에 ALTER TABLE 없이 바로 사용 가능. 스키마 마이그레이션은 실수 여지가 많으므로 초기에 확정된 스키마는 미리 생성.
