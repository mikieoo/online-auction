# D20: 부하 테스트 — 숫자로 병목을 찾고, 고치고, 다시 재기

## 오늘 한 일

k6로 시나리오 세 개를 만들어 전체 스택(서비스 5개 + MySQL·Redis·Kafka)을 컨테이너로 띄운 상태에서 쟀다. 여러 경매에 입찰이 흩어지는 시나리오에서 bid-service의 DB 커넥션 풀이 먼저 고갈되는 것을 Prometheus 지표로 확인했고, 원인은 입찰 트랜잭션 안의 auction-service 조회(Feign)였다. 조회를 락·트랜잭션 밖으로 옮긴 뒤 같은 조건으로 다시 재서 p95가 692ms → 270ms, 충돌(409)이 156건 → 0건이 됐다.

```
k6 컨테이너 ─(Docker 네트워크)─▶ gateway ─▶ bid ─▶ auction (Feign)
     │                                     └─▶ MySQL / Redis
     └─ remote write ─▶ Prometheus ◀─ 서비스 5개 /actuator/prometheus
                            └─▶ Grafana (한 시간축에서 부하와 서비스 지표를 같이 본다)
```

---

## 1. 측정 환경

- `infra/k6/compose.loadtest.yml` 오버레이: 프로젝트 이름 `auction-loadtest`(개발 DB와 분리), gateway에 `local` 프로필(토큰 발급기), Prometheus remote-write 수신.
- k6 `0.54.0`을 같은 Docker 네트워크에서 실행. 호스트에 설치하지 않아도 되고, 게이트웨이를 컨테이너 이름으로 부른다.
- 머신: Apple Silicon 10코어, Docker에 메모리 8GB. **k6와 서비스가 같은 PC에서 CPU를 나눠 쓰므로 절대 수치보다 전후 비교로 읽는다.**
- 지표는 측정 구간만 본다. 시나리오 1은 10초 워밍업(초당 5건)을 따로 두고 `phase:measure` 태그로 분리했다. 첫 요청들은 JIT·커넥션 풀 초기화로 1초 가까이 걸려 p95를 왜곡했다.

## 2. 시나리오

| 스크립트 | 상황 | 보는 것 |
|---|---|---|
| `hot-auction.js` | 경매 하나에 입찰 집중 (마감 직전) | 분산 락이 줄을 세울 때의 지연, 락 대기 3초 초과(409)가 생기는 도착률, 끝난 뒤 ACTIVE 1개·최고가 일치 |
| `bid-throughput.js` | 경매 50개에 분산, 도착률 점증 | 경매 단위 락끼리는 안 막으므로 공유 자원(커넥션 풀·CPU)의 한계 |
| `settlement-drain.js` | 경매 200개 동시 마감 | 마감 → gRPC 낙찰 확정 → outbox → Kafka → 결제 → 완료까지 걸리는 시간, 경매별 최종 상태 |

입찰 결과는 업무 단위로 분류해 셌다: `accepted`(201), `too_low`(400, 정상 업무 거절), `conflict`(409 `BID_CONFLICT` — 락 대기 초과 또는 `@Version` 충돌), `unavailable`(503), `error`(그 외). 시스템 실패(`unavailable`, `error`)만 0을 요구하고 `too_low`는 세기만 한다.

시나리오 1·2의 입찰 금액은 k6 반복 번호로 올린다. 동시에 도착한 요청은 락 안에서 순서가 섞이므로 늦게 처리된 낮은 금액이 `too_low`가 된다. 도착률이 높을수록 `too_low`가 늘어나는 건 이 생성 방식 때문이고 결함이 아니다.

## 3. 발견: 트랜잭션 안의 원격 호출이 커넥션 풀을 고갈시켰다

시나리오 2를 초당 200건까지 올렸을 때는 p95 21ms, 실패 0이었다. 600건까지 올리자 무너졌다.

| 지표 (bid-service) | 저부하 | 초당 600건 목표 |
|---|---|---|
| Hikari 사용 중 커넥션 | 일부 | **10 / 10** |
| 커넥션 대기 요청 최대 | 0 | **29** |
| 커넥션 1회 보유 시간 | 4ms | **58ms** |
| 그중 auction 조회(Feign) 시간 | 5ms | **48ms** |

경매당으로는 초당 12건이라 경매 단위 락은 원인이 아니었다. 원인은 `BidService.placeBid`가 `@Transactional` 안에서 auction-service를 조회한 것이다. Spring의 트랜잭션은 시작할 때 커넥션을 잡으므로, 커넥션이 네트워크 응답을 기다리는 동안 묶인다. 부하로 조회가 48ms로 느려지자 풀 10개 ÷ 0.058초 ≈ **초당 170건이 상한**이 됐다.

이건 D3에서 "요청 1건당 조회 1회라 커넥션 점유가 요청 범위로 끝나니 허용한다"고 예외로 둔 지점이다. 순회가 없다는 논리는 맞았지만, **상류가 느려지는 순간 보유 시간이 상류 응답 시간에 끌려간다**는 점을 놓쳤다. D7 분산 락을 도입할 때 재구성하기로 적어 두고 빠뜨린 작업이기도 하다.

같은 구조가 두 번째 문제도 만들고 있었다. 입찰 분산 락의 임대 시간은 5초인데, 락 안에서 하는 조회의 최악 시간은 connect 2초 + read 5초 = 7초다. auction-service가 느린 순간 락이 처리 도중 풀리고 다음 요청이 같은 경매에 들어온다. 첫 입찰 두 건이 그렇게 겹치면 `@Version`도 INSERT는 막지 못해 ACTIVE 입찰이 2개가 된다(그 경매의 입찰·정산 정지).

## 4. 수정: 조회 → 락 → 짧은 트랜잭션

```
전: 락 획득 → [트랜잭션: auction 조회 → 본인·상태·마감·금액 검사 → 저장] → 락 해제
후: prepareBid(auction 조회 → 본인·상태 검사) → 락 획득 → [트랜잭션: 마감·금액 검사 → 저장] → 락 해제
```

- `BidService.prepareBid`: 락·트랜잭션 없음. 형식 → 조회 → 판매자 본인 → 상태.
- `BidService.placeBid(bidderId, request, auction)`: `@Transactional`. 마감 시각 → 금액 → OUTBID·저장.
- `BidLockFacade`: prepareBid → 락 → placeBid → 해제. 거절될 요청(본인 입찰, 비활성 경매, 상류 장애)은 락 대기열에 서지 않는다.

**오래된 조회 값은 괜찮은가?** 조회 값은 락 대기(최대 3초)만큼 오래될 수 있다. 그래서 마감 검사를 락을 잡은 뒤 트랜잭션 안에서 그 시점 시각으로 한다. ACTIVE에서 바뀔 수 있는 상태는 CLOSED뿐이고 CLOSED는 end_time이 지나야 되므로, 마감 검사가 오래된 status의 빈틈까지 막는다. 검사 순서(형식 → 조회 → 본인 → 상태 → 마감 → 금액)는 그대로다.

## 5. 수정 후 재측정

**시나리오 2 (경매 50개, 초당 600건까지 점증, 3분)**

| | 수정 전 | 수정 후 |
|---|---|---|
| p95 / 최대 | 692ms / 5.9s | **270ms** / 1.68s |
| 수락 | 49,033 | 52,490 |
| 충돌 409 | 156 | **0** |
| k6가 제때 못 보낸 요청 | 3,937 | 577 |
| 커넥션 대기 최대 / 사용 최대 | 29 / 10 | **0 / 4** |

초당 600건에서 p95 270ms가 남는 건 커넥션이 아닌 다음 병목이다. 이때 bid-service·MySQL CPU가 각각 200% 가까이 쓰였고 k6도 같은 머신에 있었다. 이 이상은 같은 PC에서 재는 의미가 작다.

**시나리오 1 (경매 하나, 30초)**

| 초당 도착 | 수정 전 p95 | 수정 후 p95 | 409 (전 → 후) |
|---|---|---|---|
| 30 | 25ms | — | 0 |
| 60 | 24ms | — | 0 |
| 100 | 43ms | 26ms | 0 → 0 |
| 150 | **2.17s** | **151ms** | 15 → 0 |
| 250 | — | 412ms | — → 0 |

락 안에 DB 작업만 남아 락 보유 시간이 줄었고, 경매 하나의 처리 상한이 초당 약 100건에서 약 250건(수락 + 금액 부족 합계)으로 올라갔다. 모든 실행에서 불변 조건(ACTIVE 1개, 그 금액이 최고가)이 지켜졌다.

**시나리오 3 (경매 200개 동시 마감)**

| 항목 | 값 |
|---|---|
| 마지막 경매가 끝날 때까지 | **23.3초** |
| 경매별 마감 → 최종 상태 | 최소 5.2s, 중앙값 15.0s, 최대 23.3s |
| 최종 상태 검증 | 200 / 200 일치 (정상 160 → COMPLETED, 결제 실패 20 → 차순위 승계 → COMPLETED, 유찰 20 → FAILED) |

스케줄러 로그로 틱을 재 보면 마감 200건 + 정산 50건 틱이 1.39초, 정산만 50건인 틱이 0.5~0.8초(건당 10~16ms)다. 5초 주기의 15% 정도만 쓴다. 그래서 200건이 23초 걸린 건 처리 속도가 아니라 `settlement-batch-size: 50` × 5초 주기가 정한 값이다(200 ÷ 50 = 4틱).

배치 상한을 올리면 마감 폭주가 빨리 빠지지만, 올리지 않았다. 상한은 "상류가 느릴 때 한 틱의 최악 시간"을 묶는 장치이기 때문이다. 브레이커는 실패(타임아웃 포함)는 세지만 **느린 성공**은 세지 않는다(slow-call 설정 없음). 건당 1초로 느리게 성공하는 상황에서 상한이 200이면 한 틱이 200초가 되어 ShedLock `lockAtMostFor`(30초)를 넘고 정산이 중복 실행된다. 올리려면 slow-call 기반 브레이커나 틱 시간 예산(경과 시간이 N초를 넘으면 남은 건을 다음 틱으로)을 먼저 넣어야 한다.

## 6. 남은 것 (`docs/tracking/findings.md`)

- 같은 상품의 WAITING 경매 둘을 동시에 시작하면 ACTIVE가 2개가 된다(조회 후 검사, 락 없음).
- Redis 장애로 락이 무력화되면 첫 입찰 동시 INSERT로 ACTIVE 입찰이 2개가 될 수 있다. 근본 방어는 생성 컬럼 + UNIQUE.
- 차순위 승계가 결제 실패한 입찰자의 다른 입찰을 다시 고를 수 있다.
- Outbox 발행기의 head-of-line blocking과 트랜잭션 안 Kafka 전송.

## 면접 대비 포인트

**Q: 부하 테스트로 뭘 찾았나?**
→ 경매 여러 개에 초당 600건을 흩뿌리자 p95가 692ms로 꺾였다. 경매당 12건이라 분산 락은 아니었고, Prometheus에서 bid-service Hikari 풀이 10/10에 대기 29건인 것을 봤다. 커넥션 보유 시간 58ms 중 48ms가 auction-service 조회였다 — 입찰 트랜잭션 안에서 원격 호출을 하고 있었다. 조회를 락·트랜잭션 밖으로 옮겨 p95 270ms, 409 0건, 커넥션 대기 0이 됐다.

**Q: 트랜잭션 안의 원격 호출이 왜 문제인가? 요청당 한 번뿐인데.**
→ 커넥션 보유 시간이 내 DB 작업이 아니라 상대 서비스의 응답 시간에 묶인다. 평소 5ms면 티가 안 나지만, 부하로 상대가 느려지는 바로 그 순간 풀이 고갈되어 장애가 번진다. 풀 크기 ÷ 보유 시간이 처리량 상한이다.

**Q: 조회를 락 밖으로 빼면 오래된 값으로 검증하지 않나?**
→ 최대 락 대기 3초만큼 오래될 수 있다. 그래서 마감 검사는 락을 잡은 뒤 그 시점 시각으로 한다. ACTIVE에서 바뀔 수 있는 상태는 CLOSED뿐이고 CLOSED는 마감 시각이 지나야 되므로 마감 검사가 그 빈틈을 함께 막는다. 상태 전이가 늘어나면 이 전제를 다시 봐야 한다.

**Q: 분산 락의 임대 시간은 어떻게 정해야 하나?**
→ 락 안 최악 처리 시간보다 길어야 한다. 아니면 처리 도중 락이 풀려 직렬화가 깨진다. 이 프로젝트는 락 안에 원격 호출(최악 7초)이 있어 임대 5초를 넘을 수 있었고, 호출을 락 밖으로 빼서 락 안에는 DB 작업만 남겼다. 워치독(임대 자동 연장)은 처리 시간을 몰라도 되지만, 인스턴스가 죽으면 30초간 락이 남는다.

**Q: 정산 배치 상한을 올리면 마감 폭주가 빨리 끝나지 않나?**
→ 정상일 때 50건 틱은 0.5~0.8초라 여유는 있다. 하지만 상한은 상류가 느릴 때 한 틱의 최악 시간을 묶는 장치다. 브레이커는 느린 성공을 실패로 세지 않으므로, 상한만 올리면 한 틱이 ShedLock 락 시간을 넘어 중복 실행된다. slow-call 브레이커나 틱 시간 예산이 먼저다.

**Q: 같은 PC에서 잰 숫자를 믿을 수 있나?**
→ 절대 수치는 못 믿는다. k6와 서비스가 CPU를 나눠 쓴다. 그래서 같은 조건에서 수정 전후를 비교했고, 병목 판단은 지연이 아니라 서비스 내부 지표(커넥션 대기·보유 시간)로 했다.
