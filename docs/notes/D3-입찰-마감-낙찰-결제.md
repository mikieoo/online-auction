# D3: 입찰 → 마감 → 낙찰 → 결제, 동기 REST로 끝까지 연결하기

## 오늘 한 일

bid-service에 입찰 접수·검증 API를, auction-service에 ShedLock 기반 마감·정산 스케줄러를, payment-service에 멱등한 결제 생성 API를 구현했다. 세 서비스는 OpenFeign으로 동기 호출하며, 세 개를 실제로 띄워 "입찰 → 마감 → 낙찰 → 결제 → COMPLETED"가 자동으로 흘러가는 것을 확인했다. 오류 응답은 `{ code, message }` 형태로 표준화하고, 코드와 문서가 어긋나 있던 상태 집합(Bid, Payment)과 스키마를 문서 기준으로 정리했다.

```
[bidder] --POST /api/v1/bids--> bid-service --GET /api/v1/auctions/{id}--> auction-service
                                                                               │
          (5초마다)  auction-service 스케줄러 ──A단계: ACTIVE & end_time 지남 → CLOSED
                                            └─B단계: CLOSED & winner 없음
                                                 ├─POST /internal/v1/bids/auctions/{id}/winner → bid-service
                                                 └─POST /internal/v1/payments                 → payment-service
```

Kafka는 D8부터라, 낙찰→결제 구간은 오늘은 동기 호출이다. D9에서 `AuctionWon` 이벤트로 바뀔 임시 구조라는 걸 알고 만들었고, 그 전제를 코드 주석과 결정 기록에 남겼다.

## 1. 입찰 검증 — 순서가 곧 규칙이다

```java
@Transactional
public Bid placeBid(Long bidderId, PlaceBidRequest request) {
    // 1. 형식: amount 필수, 0 초과                     → 400 INVALID_REQUEST
    // 2. 경매 조회 (auction-service, Feign)            → 404 / 503 / 502
    AuctionSummaryResponse auction = fetchAuction(auctionId);
    // 3. 판매자 본인                                    → 403 SELLER_CANNOT_BID
    if (bidderId.equals(auction.getSellerId())) throw new SellerCannotBidException(auctionId);
    // 4. 상태 ACTIVE + 마감시간 미경과                  → 409 AUCTION_NOT_ACTIVE / AUCTION_ALREADY_ENDED
    if (!"ACTIVE".equals(auction.getStatus())) throw new AuctionNotActiveException(...);
    if (!auction.getEndTime().isAfter(LocalDateTime.now(clock))) throw new AuctionAlreadyEndedException(auctionId);
    // 5. 금액 규칙: 첫 입찰 >= 시작가 / 이후 > 현재 최고가 + 1000  → 400 BID_AMOUNT_TOO_LOW
    Optional<Bid> currentActive = bidRepository.findByAuctionIdAndStatus(auctionId, BidStatus.ACTIVE);
    ...
    // 6. 이전 ACTIVE는 OUTBID로, 새 입찰은 ACTIVE로 저장
    currentActive.ifPresent(previous -> { previous.markOutbid(); bidRepository.save(previous); });
    return bidRepository.save(new Bid(auctionId, bidderId, amount));
}
```

**왜 이 순서인가?** 싼 검사에서 비싼 검사로, 그리고 "의미가 없어지는" 검사를 먼저. 금액 형식이 틀렸으면 경매를 조회할 이유가 없고, 판매자 본인이면 상태를 볼 이유가 없다. 검사 순서를 문서(business-rules)에 적어 두면 "왜 403이 아니라 409가 왔지?" 같은 질문에 바로 답할 수 있다.

**한 경매에 ACTIVE Bid는 최대 1개.** 새 입찰이 받아들여지는 순간 이전 ACTIVE는 OUTBID가 된다. 같은 사람이 자기 입찰가를 올려도 마찬가지다. 그래서 "현재 최고가"는 `MAX(amount)`가 아니라 "ACTIVE인 Bid 하나"이고, 낙찰 확정도 그 하나를 WINNER로 바꾸는 일이 된다.

**마감시간 검사를 왜 bid-service에서도 하나?** 마감은 스케줄러가 5초 주기로 돌기 때문에, 마감시간이 지나도 최대 5초 동안 경매 상태는 ACTIVE다. 그 틈에 들어오는 입찰을 `endTime`으로 한 번 더 막는다. 그래도 남는 경합(검사와 저장 사이)은 D7의 분산 락에서 다룬다 — 오늘은 코드에 "D7 예정"이라고만 적었다.

### Feign 오류를 우리 오류로 바꾸기

```java
public class AuctionClientErrorDecoder implements ErrorDecoder {
    @Override
    public Exception decode(String methodKey, Response response) {
        if (response.status() == 404) return new AuctionNotFoundException(...);   // 404 그대로 전달
        if (response.status() >= 500) return new UpstreamUnavailableException(...); // 503
        return new UpstreamErrorException(...);                                    // 502
    }
}
```

여기서 하나 배운 것: **연결 거부와 타임아웃은 `ErrorDecoder`를 거치지 않는다.** HTTP 응답이 없으니 디코딩할 게 없고, `feign.RetryableException`으로 바로 올라온다. 그래서 `BidService`가 `FeignException`을 한 번 더 잡아 503으로 바꾼다. 디코더만 등록하고 끝냈으면 auction-service가 꺼져 있을 때 500이 나갔을 것이다.

## 2. 마감·정산 스케줄러 — ShedLock과 트랜잭션 경계

### 왜 ShedLock인가

`@Scheduled`는 인스턴스마다 돈다. K8s에서 auction-service를 2개로 늘리면 같은 경매를 두 인스턴스가 동시에 마감하려 든다. ShedLock은 DB 테이블(`shedlock`)의 행 하나를 락으로 써서 **한 번에 한 인스턴스만** 스케줄 메서드를 실행하게 한다.

```java
@Configuration
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "PT30S")
public class SchedulerConfig {
    @Bean
    public LockProvider lockProvider(DataSource dataSource) {
        return new JdbcTemplateLockProvider(
                JdbcTemplateLockProvider.Configuration.builder()
                        .withJdbcTemplate(new JdbcTemplate(dataSource))
                        .usingDbTime()   // 인스턴스 시계가 아니라 DB 시계 기준
                        .build());
    }
}
```

- `lockAtMostFor = 30s`: 락을 잡은 인스턴스가 죽어서 락을 못 풀었을 때, 최대 30초 뒤엔 다른 인스턴스가 가져간다. 정상 실행이 30초를 넘으면 **중복 실행이 가능**하다는 뜻이기도 하다. 그래서 B단계는 틱당 50건 상한을 두고, `application.yml`에 "50건 × (5s + 5s 타임아웃) = 최악 500s > 30s"라는 계산을 주석으로 남겼다. 다운스트림이 전부 타임아웃 나는 상황에서만 문제고, 중복 실행돼도 모든 호출이 멱등이라 데이터는 깨지지 않는다.
- `lockAtLeastFor = 1s`: 실행이 너무 빨리 끝나 인스턴스 간 시계 차이로 다른 인스턴스가 곧바로 다시 잡는 것을 막는다.
- `usingDbTime()`: 락 만료 판정을 DB 시계로 한다. 인스턴스마다 시계가 다르면 락이 이상하게 풀린다.

### 두 단계로 나눈 이유, 그리고 트랜잭션 밖의 Feign

```java
@Scheduled(fixedDelayString = "${scheduler.auction.fixed-delay:5000}")
@SchedulerLock(name = "auction-settlement", lockAtLeastFor = "PT1S")
public void settle() {
    closeEndedAuctions();    // A단계: ACTIVE & end_time 지남 → CLOSED. 외부 호출 없음.
    settleClosedAuctions();  // B단계: CLOSED & winner 없음 → 낙찰 확정 → 결제 → COMPLETED/CLOSED/FAILED
}
```

**A단계는 외부 호출이 없어서 항상 성공한다.** bid-service가 죽어 있어도 마감은 된다. 마감이 되면 bid-service는 상태를 보고 입찰을 거절할 수 있다. 마감과 정산을 한 트랜잭션에 넣었으면 bid-service 장애가 "마감도 안 되는" 장애로 번진다.

**스케줄러 빈에는 `@Transactional`이 없다.** DB 작업은 `AuctionSettlementService`의 메서드로 위임하고, 메서드 하나 = 경매 한 건 = 트랜잭션 하나다.

```java
// 스케줄러 빈 (트랜잭션 없음)
WinnerResponse winner = bidClient.confirmWinner(auctionId);          // Feign — 트랜잭션 밖
...
PaymentResponse payment = paymentClient.requestPayment(paymentRequest); // Feign — 트랜잭션 밖
switch (payment.getStatus()) {
    case COMPLETED -> settlementService.completeWithWinner(auctionId, winnerId, amount); // 트랜잭션 1개
    case FAILED    -> settlementService.recordPaymentFailed(auctionId, winnerId, amount);  // 트랜잭션 1개
    case REQUESTED -> log.info("다음 주기에 재확인");
}
```

두 가지 함정을 피하려고 이렇게 나눴다:

1. **자기 호출(self-invocation)에는 `@Transactional`이 안 걸린다.** 프록시가 감싸는 건 빈의 바깥에서 들어오는 호출이다. 같은 클래스 안에서 `this.closeAuction()`을 부르면 트랜잭션이 없다. 별도 빈으로 빼야 한다.
2. **트랜잭션 안에서 원격 호출을 하면 DB 커넥션을 원격 응답 시간만큼 붙잡는다.** 타임아웃 5초짜리 Feign 호출이 트랜잭션 안에 있으면 커넥션 풀이 5초씩 잠긴다. 경매 50건이면 풀이 고갈된다.

한 경매에서 예외가 나면 WARN 로그를 남기고 **다음 경매로 넘어간다.** 한 건이 루프를 중단시키면 나머지 경매가 영원히 정산되지 않는다.

### 재시도는 "다음 틱", 그러니 전부 멱등해야 한다

Feign 호출이 실패하면(연결 거부, 타임아웃, 5xx) **아무것도 저장하지 않고** 다음 틱에 다시 집는다. 재시도 로직을 Feign Retryer에 두지 않은 이유는, 재시도가 이미 스케줄러 주기로 존재하기 때문이다. 이중 재시도는 타임아웃 합을 키워 ShedLock 만료 위험만 높인다.

그 대신 재시도 경로가 전부 멱등이어야 한다:

- **낙찰 확정**: 이미 WINNER가 있으면 그것을 돌려준다.
- **결제 요청**: 같은 `idempotencyKey`(`{auctionId}-{winnerId}-{reassignmentCount}`)면 기존 Payment를 돌려준다.

### "입찰 없음"은 404가 아니다

처음 설계에서는 낙찰 확정 API가 입찰이 없으면 404를 주고, auction-service가 404를 유찰(FAILED)로 해석하려 했다. 리뷰에서 걸렸다: **404는 경로 오타, 배포 불일치, 게이트웨이 라우팅 오류로도 난다.** FAILED는 되돌릴 수 없는 전이인데, 인프라 오류 하나로 경매가 영구 유찰될 수 있다. 그래서 입찰 없음은 HTTP 200에 본문으로 표현한다.

```json
{ "auctionId": 3, "hasBids": false, "winningBid": null }
```

비 2xx는 전부 "다음 틱에 재시도"로 통일된다. 유찰 판정은 오직 `hasBids=false`일 때만.

### D3 한정 임시 인코딩: status + winner_id

정산 진행 단계를 표현할 컬럼을 새로 만들지 않고, `status`와 `winner_id` 조합으로 표현했다.

| status | winner_id | 의미 |
|---|---|---|
| CLOSED | NULL | 정산 대기(B단계 대상) |
| CLOSED | 있음 | 결제 실패, D10 차순위 승계 대기 |
| COMPLETED | 있음 | 결제 성공 |
| FAILED | NULL | 유찰 |

낙찰자(`winner_id`)를 **결제 결과와 함께만** 저장하는 게 핵심이다. 그래야 "CLOSED이면서 winner 없음 = 아직 정산 안 됨"이 성립하고, 결제 실패 건은 winner가 채워져 재시도 대상에서 빠진다. 대신 결제가 끝나기 전까지 클라이언트는 낙찰자를 볼 수 없고, architecture.md의 "낙찰자 설정 → 결제" 순서와도 다르다. D9에서 `AuctionWon` 이벤트를 발행하려면 낙찰자를 먼저 확정해야 하므로 그때 재설계한다. 이 사실을 `docs/tracking/decisions/0002`에 기록했다.

## 3. 결제 시뮬레이션 — 결정적으로 실패시키기

```java
public boolean isFailure(BigDecimal amount) {
    String integerPart = amount.toBigInteger().toString();
    return integerPart.endsWith(failureSuffix);   // 기본 "9999"
}
```

19,999원은 실패, 20,000원은 성공. **랜덤 실패율은 쓰지 않았다.** D10에서 "결제 실패 → 차순위 승계" 시나리오를 테스트할 때 입찰가만으로 실패를 정확히 재현해야 한다. 랜덤이면 테스트가 불안정해진다.

### 멱등성과 UNIQUE 위반, 그리고 rollback-only

```java
@Service
public class PaymentService {                       // @Transactional 없음 — 의도적
    public PaymentProcessResult process(PaymentRequest request) {
        Optional<Payment> existing = paymentRepository.findByIdempotencyKey(key);
        if (existing.isPresent()) return PaymentProcessResult.existing(ensureSettled(existing.get()));
        try {
            return PaymentProcessResult.created(transactionService.createAndSettle(...)); // 별도 빈, @Transactional
        } catch (DataIntegrityViolationException e) {
            // 동시 요청이 먼저 INSERT한 경우. 실패한 트랜잭션은 이미 끝났으니 여기서 재조회한다.
            Payment winner = paymentRepository.findByIdempotencyKey(key).orElseThrow(() -> e);
            return PaymentProcessResult.existing(ensureSettled(winner));
        }
    }
}
```

같은 키로 두 요청이 동시에 들어오면 한쪽은 UNIQUE 제약에 걸린다. 그때 "기존 건을 다시 조회해서 돌려주면 되지"가 생각보다 까다롭다. **`DataIntegrityViolationException`이 나면 그 트랜잭션은 rollback-only로 표시**되어, 같은 트랜잭션 안에서 재조회하고 정상 반환해도 커밋 시점에 `UnexpectedRollbackException`이 난다. 그래서 파사드(`PaymentService`)는 트랜잭션이 없고, 생성·확정만 `PaymentTransactionService`의 트랜잭션에서 하고, 재조회는 그 트랜잭션이 끝난 뒤 파사드에서 한다.

`saveAndFlush`를 쓴 이유도 같다. 그냥 `save`면 INSERT가 커밋 시점까지 미뤄져 UNIQUE 위반이 `createAndSettle` 호출 시점에 드러나지 않는다.

### REQUESTED로 남은 결제

payment-service가 저장 직후, 시뮬레이션 전에 죽으면 REQUESTED 상태의 Payment가 남는다. 다음 틱에 auction-service가 같은 키로 다시 요청하면 기존 건을 만나는데, 그게 REQUESTED면 **재시뮬레이션해서 확정한 뒤** 돌려준다. auction-service 쪽에서도 REQUESTED 응답은 "다음 틱에 재확인"으로 취급한다. 두 쪽이 서로를 보완한다.

## 4. 오류 응답 표준화와 `/internal` 경로

D2까지는 모든 예외가 500이었다. 오늘부터 세 서비스가 같은 형태로 응답한다.

```json
{ "code": "AUCTION_NOT_ACTIVE", "message": "진행 중인 경매에만 입찰할 수 있습니다. auctionId=7, 현재 상태: WAITING" }
```

| HTTP | 언제 | code 예 |
|---|---|---|
| 400 | 값 검증 실패, 금액 규칙 위반 | `INVALID_REQUEST`, `BID_AMOUNT_TOO_LOW` |
| 403 | 본인 경매 입찰, 타인 결제 조회 | `SELLER_CANNOT_BID`, `FORBIDDEN` |
| 404 | 없는 리소스, 없는 경로 | `AUCTION_NOT_FOUND`, `NOT_FOUND` |
| 409 | 상태 위반 | `AUCTION_ALREADY_ENDED`, `INVALID_STATE_TRANSITION` |
| 502 / 503 | 상류 서비스 4xx / 연결 실패·타임아웃·5xx | `UPSTREAM_ERROR`, `UPSTREAM_UNAVAILABLE` |

서비스별 `@RestControllerAdvice` 하나가 도메인 예외(상태·코드를 들고 있는 예외 클래스)와 스프링 예외(`MethodArgumentNotValidException`, `MissingRequestHeaderException`, `NoResourceFoundException` 등)를 전부 매핑한다. 스모크 테스트에서 없는 경로가 500으로 나오는 걸 보고 `NoResourceFoundException` → 404를 뒤늦게 추가했다. 빌드가 초록이어도 실제로 띄워 보면 이런 게 나온다.

**서비스 간 내부 API는 `/internal/v1/...`로 분리했다.** 낙찰 확정과 결제 생성은 인증 없이 호출되는 내부 API인데, `/api/v1` 아래에 두면 D4 게이트웨이가 그대로 외부에 노출한다. 경로 접두사로 구분해 두면 게이트웨이는 `/api/**`만 라우팅하면 된다.

## 5. 코드와 문서가 어긋나 있던 것들

D2 코드와 D1 문서(business-rules.md)를 나란히 놓고 보니 세 곳이 달랐다.

| 항목 | 코드(D2) | 문서(D1) | 정리 |
|---|---|---|---|
| Bid 상태 | ACTIVE / WINNING / OUTBID / CANCELLED | ACTIVE / OUTBID / WINNER, 취소 없음 | 문서대로. `cancel()` 삭제 — "입찰 철회 불가" 규칙과 모순 |
| Payment 상태 | PENDING | REQUESTED (DB 기본값도 REQUESTED) | 문서대로. `failure_reason` 컬럼도 DB에 없었음 → 추가 |
| bid 테이블 | 엔티티는 `created_at`으로 매핑 | 스키마는 `bid_time` | 실행하면 바로 SQL 오류. `created_at`으로 통일 |

문서를 기준으로 코드를 고쳤다. D1에서 합의한 규칙이 원본이고, 코드는 그걸 구현한 것이기 때문이다. 스키마 변경(ShedLock 테이블, 컬럼 추가·개명)이 있어서 로컬 DB는 `docker compose down -v`로 다시 만들어야 한다.

덤으로 하나 더: Windows에서 체크아웃하면 `.sh` 파일이 CRLF가 되어 MySQL 컨테이너의 초기화 스크립트가 `/bin/bash^M: bad interpreter`로 죽는다. `.gitattributes`에 `*.sh text eol=lf`를 추가했다.

## 면접 대비 포인트

**Q: 스케줄러가 여러 인스턴스에서 돌면 어떻게 중복 실행을 막나?**
→ ShedLock. DB 테이블의 행 하나를 락으로 써서 스케줄 메서드를 한 인스턴스만 실행한다. `lockAtMostFor`는 인스턴스가 죽었을 때 락이 풀리는 최대 시간이자, 정상 실행이 이 시간을 넘으면 중복 실행이 가능해지는 경계다. 그래서 틱당 처리량에 상한을 두고, 중복 실행돼도 안전하도록 모든 호출을 멱등하게 만든다. Redis 락(Redisson)으로도 가능하지만, 스케줄러 락은 초 단위 정밀도면 충분해서 이미 있는 DB를 쓰는 게 의존성이 적다.

**Q: 왜 `@Transactional` 안에서 외부 API를 호출하면 안 되는가?**
→ 트랜잭션은 DB 커넥션을 점유한다. 안에서 5초 타임아웃짜리 원격 호출을 하면 커넥션이 5초 동안 잠기고, 건수가 늘면 커넥션 풀이 고갈된다. 또 원격 호출이 성공했는데 커밋이 실패하면 "결제는 됐는데 경매는 CLOSED"처럼 두 시스템이 어긋난다. 원격 호출은 트랜잭션 밖에서 하고, 결과를 받아 짧은 트랜잭션으로 저장한다.

**Q: 같은 클래스 안에서 `@Transactional` 메서드를 호출하면 왜 트랜잭션이 안 걸리나?**
→ 스프링 AOP는 프록시 기반이다. 트랜잭션은 프록시 객체를 거쳐 들어오는 호출에만 적용되는데, `this.method()`는 프록시를 거치지 않는다. 별도 빈으로 분리하거나 자기 자신을 주입받아 호출해야 한다.

**Q: 멱등성 키로 중복 결제를 막을 때 동시 요청은 어떻게 처리하나?**
→ 조회-후-생성은 두 요청이 동시에 "없음"을 보고 둘 다 INSERT할 수 있다. 최종 방어선은 DB UNIQUE 제약이고, 위반한 쪽은 기존 건을 재조회해 돌려준다. 단, UNIQUE 위반이 나면 그 트랜잭션은 rollback-only가 되므로 재조회는 트랜잭션 밖에서 해야 한다. 그래서 비트랜잭션 파사드 + 트랜잭션 서비스로 나눴다.

**Q: 재시도는 어디서 해야 하나 — 클라이언트(Feign Retryer)인가, 스케줄러 주기인가?**
→ 재시도 지점은 하나여야 한다. 이미 5초 주기 스케줄러가 "실패한 건을 다음 틱에 다시 집는" 재시도 역할을 하므로 Feign 레벨 재시도를 겹치지 않았다. 겹치면 한 틱의 최악 실행 시간이 늘어 ShedLock 만료와 충돌한다. 대신 재시도 경로가 전부 멱등해야 한다는 조건이 붙는다.

**Q: "결과 없음"을 404로 표현하면 안 되는 경우는?**
→ 호출자가 그 응답으로 되돌릴 수 없는 결정을 내릴 때. 404는 경로 오타·배포 불일치·라우팅 오류로도 발생하므로, "입찰 없음 → 유찰(FAILED)"을 404에 태우면 인프라 오류가 경매를 영구 유찰시킨다. 비즈니스 결과는 200 본문으로 명시적으로 표현하고, HTTP 오류는 전부 "재시도"로 다루는 게 안전하다.
