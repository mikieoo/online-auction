# D7: 분산 락 — Redisson으로 동시 입찰을 한 줄로 세우기

## 오늘 한 일

D6의 낙관적 락(충돌 → 실패 → 재시도)을 Redisson 분산 락으로 대체했다. 이제 같은 경매에 동시 입찰이 들어오면 한 명씩 순서대로 처리된다. 실패(409) 대신 정상 업무 거절(400 금액 부족)이 나온다.

---

## 1. D6 vs D7 — 실기동 비교

같은 경매에 10개 동시 입찰:

| | D6 (낙관적 락) | D7 (분산 락) |
|---|---|---|
| 성공 | 1 | 1 |
| 거절 사유 | `BID_CONFLICT` (409) — version 충돌 | `BID_AMOUNT_TOO_LOW` (400) — 금액 부족 |
| 거절 건수 | 9 | 9 |
| 읽기 경합 | 있음 (모두 같은 ACTIVE를 읽음) | 없음 (순서대로 최신 상태를 읽음) |
| 클라이언트 재시도 필요 | 필수 | 불필요 (정상 거절) |

핵심 차이: D6에서 9개 요청은 "나는 유효한 입찰을 했는데 서버가 충돌로 거부했다"(→ 재시도 필요). D7에서 9개 요청은 "내 금액이 이미 올라간 가격보다 낮다"(→ 더 높은 금액으로 다시 입찰).

## 2. 구조 — 락이 트랜잭션 바깥에 있어야 하는 이유

```
BidController
  └─ BidLockFacade.placeBidWithLock()
       ├─ 1. Redisson 분산 락 획득 (bid:auction:{auctionId})
       ├─ 2. BidService.placeBid() ← @Transactional
       │     ├─ Feign으로 경매 조회
       │     ├─ 금액 검증
       │     ├─ 이전 ACTIVE → OUTBID
       │     └─ 새 Bid 저장
       └─ 3. 락 해제
```

락이 `@Transactional` **안에** 있으면: 트랜잭션 커밋 전에 락이 풀리고, 커밋이 DB에 반영되기 전에 다음 스레드가 락을 획득해서 아직 커밋 안 된 데이터를 읽을 수 있다. 그래서 Facade 패턴으로 락을 트랜잭션 바깥에 둔다.

## 3. Redisson 분산 락 핵심 코드

```java
@Component
public class BidLockFacade {
    private static final String LOCK_KEY_PREFIX = "bid:auction:";
    private static final long WAIT_TIME_SECONDS = 3;   // 대기 시간
    private static final long LEASE_TIME_SECONDS = 5;   // 임대 시간 (자동 해제)

    public Bid placeBidWithLock(Long bidderId, PlaceBidRequest request) {
        RLock lock = redissonClient.getLock(LOCK_KEY_PREFIX + auctionId);
        boolean acquired = false;
        try {
            acquired = lock.tryLock(WAIT_TIME_SECONDS, LEASE_TIME_SECONDS, TimeUnit.SECONDS);
            if (!acquired) throw new BidConflictException(auctionId);
            return bidService.placeBid(bidderId, request);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new BidConflictException(auctionId);
        } finally {
            if (acquired && lock.isHeldByCurrentThread()) lock.unlock();
        }
    }
}
```

### tryLock 파라미터

- **waitTime (3초)**: 락을 못 잡으면 최대 3초 대기. 초과하면 `BID_CONFLICT` 반환. 입찰에 3초 이상 걸리면 뭔가 잘못된 것.
- **leaseTime (5초)**: 락 잡은 후 5초 안에 처리 못 하면 자동 해제. 데드락 방지.
- **`isHeldByCurrentThread()`**: leaseTime 초과로 이미 해제된 락을 다시 해제하는 것 방지.

## 4. `@Version`은 왜 남겨두나

분산 락의 단일 장애점은 Redis다. Redis가 죽으면 락이 동작하지 않는다. 그때 `@Version` 낙관적 락이 DB 레벨에서 잡아낸다 — 계층 방어(defense in depth).

운영에서는 Redis Sentinel이나 Cluster로 Redis 가용성을 높이겠지만, 이 프로젝트에서는 단일 Redis + `@Version` 조합이 적절하다.

## 5. 면접에서 물어볼 만한 것

**Q: Redisson의 `tryLock` vs `lock`?**
- `lock()`: 무한 대기. 데드락 위험.
- `tryLock(waitTime, leaseTime, unit)`: 대기 시간 초과 시 false 반환. 프로덕션에서는 항상 `tryLock`.

**Q: leaseTime을 -1로 주면?**
- Redisson 워치독(watchdog)이 활성화된다. 30초마다 자동 갱신해서 처리가 끝날 때까지 락을 유지한다. 편리하지만 서비스가 죽으면 30초간 락이 남아있다.

**Q: 분산 환경에서 Redis 마스터가 죽으면?**
- 슬레이브가 승격될 때 락 정보가 복제 안 됐을 수 있다(비동기 복제). 이걸 막으려면 **RedLock 알고리즘** (N/2+1 노드에 락 획득)을 쓰지만, 복잡도가 높고 논쟁이 있다. 이 프로젝트에서는 `@Version` 안전망으로 충분.

**Q: 락 키를 `bid:auction:{auctionId}`로 잡은 이유?**
- 동시성 문제가 **같은 경매의 입찰**에서 발생하므로, 경매 단위로 직렬화. 다른 경매의 입찰은 병렬 처리된다. 키 단위가 너무 넓으면(전역 락) 처리량이 떨어지고, 너무 좁으면(bid별) 경합을 못 막는다.
