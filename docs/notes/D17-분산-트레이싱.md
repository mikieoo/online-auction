# D17 — 분산 트레이싱 (OpenTelemetry + Zipkin)

## 왜 필요한가

MSA에서 하나의 요청이 여러 서비스를 거친다:
```
사용자 → Gateway → auction-service → (Kafka) → payment-service
                  → bid-service (gRPC)
```

어디서 느려졌는지, 어디서 실패했는지 추적하려면 요청 하나를 관통하는 ID(trace ID)가 필요하다.

## 핵심 개념

| 용어 | 설명 |
|---|---|
| Trace | 하나의 요청이 시스템을 통과하는 전체 경로 |
| Span | Trace 안의 개별 작업 단위 (HTTP, DB, gRPC 등) |
| Trace ID | 모든 서비스에 전파되는 고유 ID |
| Span ID | 각 Span의 ID, 부모-자식 트리 구성 |

## 기술 스택

```
Spring Boot 3.3 + Micrometer Tracing (구 Sleuth 후속)
    ↓
micrometer-tracing-bridge-otel (OpenTelemetry 브릿지)
    ↓
opentelemetry-exporter-zipkin (Zipkin으로 전송)
    ↓
Zipkin UI (localhost:9411)
```

## 구현 내용

### 의존성 (root build.gradle, 모든 서비스 공통)

```groovy
implementation 'org.springframework.boot:spring-boot-starter-actuator'
implementation 'io.micrometer:micrometer-tracing-bridge-otel'
implementation 'io.opentelemetry:opentelemetry-exporter-zipkin'
```

별도 코드 없이 의존성 + 설정만으로 자동 계측됨.

### 설정 (application.yml)

```yaml
management:
  tracing:
    sampling:
      probability: 1.0    # dev: 전수 기록, prod: 0.1 등
  zipkin:
    tracing:
      endpoint: http://localhost:9411/api/v2/spans

# 로그에 trace/span ID 포함
logging:
  pattern:
    level: "%5p [${spring.application.name},%X{traceId},%X{spanId}]"

# Kafka trace 전파 (Kafka 사용 서비스만)
spring:
  kafka:
    listener:
      observation-enabled: true
    template:
      observation-enabled: true
```

### Trace 전파 경로

| 구간 | 전파 방식 |
|---|---|
| HTTP (Gateway → 서비스) | `traceparent` 헤더 (W3C 표준) |
| Feign (서비스 → 서비스) | 자동 헤더 주입 |
| gRPC (auction → bid) | gRPC metadata |
| Kafka (이벤트) | Kafka 헤더에 trace context |

### 로그 출력 예시

```
INFO [auction-service,6af3d8c2e1b4a5f0,6af3d8c2e1b4a5f0] 경매 시작 처리
INFO [bid-service,6af3d8c2e1b4a5f0,8bc2d9f3a4e5b6c1] 입찰 접수
```

같은 trace ID(6af3d8c2...)로 서비스 간 로그를 연결할 수 있다.

## Docker 환경

`application-docker.yml`에서 Zipkin 엔드포인트만 오버라이드:
```yaml
management:
  zipkin:
    tracing:
      endpoint: http://auction-zipkin:9411/api/v2/spans
```

## 샘플링

- `probability: 1.0` — 모든 요청 기록 (개발용)
- `probability: 0.1` — 10%만 기록 (프로덕션, 부하 감소)
- 전수 기록은 Zipkin 저장소와 네트워크 비용이 커서 프로덕션에서는 비율 조절 필수

## 면접 포인트

1. **왜 분산 트레이싱인가** — 로그만으로는 서비스 간 흐름 추적 불가. trace ID로 연결
2. **OpenTelemetry** — 벤더 중립 관측성 표준. 계측은 OTel, 백엔드(Zipkin/Jaeger)는 교체 가능
3. **Micrometer Tracing** — Spring Boot 3 표준. Boot 2의 Sleuth 후속
4. **Kafka 비동기 구간** — observation-enabled로 Kafka 헤더에 trace context를 넣어야 비동기 구간도 연결
5. **샘플링** — 전수 기록은 비용/성능 문제. 비율 조절 + 중요 요청은 강제 기록 가능
