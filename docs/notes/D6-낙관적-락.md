# D6: 낙관적 락 — 동시 입찰을 DB가 잡아내게 하기

## 오늘 한 일

같은 경매에 동시 입찰이 들어오면 ACTIVE Bid가 2개 생기는 D3의 경합 버그를, JPA `@Version` 낙관적 락으로 해결했다. 10개 동시 입찰에서 1개만 성공, 9개는 409로 거절되고, DB에 ACTIVE bid는 정확히 1개만 남는 것을 확인했다.

---

## 1. 문제 — 검사와 저장 사이의 빈틈

```
Thread A: findByAuctionIdAndStatus → ACTIVE = 5000원 (version=0)
Thread B: findByAuctionIdAndStatus → ACTIVE = 5000원 (version=0)

Thread A: 5000원 → OUTBID, 새 6000원 저장  ✓
Thread B: 5000원 → OUTBID, 새 7000원 저장  ✓   ← 여기가 문제
```

ACTIVE Bid가 2개가 되면, 이후 `findByAuctionIdAndStatus(ACTIVE)`가 `IncorrectResultSizeDataAccessException`을 던지며 그 경매의 입찰·정산이 영구 정지된다.

## 2. 해결 — `@Version`으로 UPDATE에 조건 걸기

```java
@Version
@Column(name = "version", nullable = false)
private Long version;
```

JPA가 생성하는 UPDATE:

```sql
UPDATE bid SET status='OUTBID', version=1
WHERE bid_id=? AND version=0
-- version이 이미 1이면 → 0 rows updated → OptimisticLockingFailureException
```

Thread B가 같은 bid를 OUTBID로 바꾸려 할 때, Thread A가 이미 version을 올려놨으므로 실패한다.

## 3. 예외 처리

`ObjectOptimisticLockingFailureException`은 `@Transactional` 커밋 시점에 발생한다 — 서비스 메서드 안에서 잡을 수 없다. `GlobalExceptionHandler`에서 처리:

```java
@ExceptionHandler(ObjectOptimisticLockingFailureException.class)
public ResponseEntity<ErrorResponse> handleOptimisticLock(
        ObjectOptimisticLockingFailureException e) {
    return ResponseEntity.status(HttpStatus.CONFLICT)
            .body(new ErrorResponse("BID_CONFLICT",
                    "다른 입찰과 동시에 처리되어 실패했습니다. 다시 시도해 주세요."));
}
```

클라이언트는 409를 받으면 재시도하면 된다. 재시도 시에는 이미 새 ACTIVE bid가 있으므로 정상 검증된다.

## 4. 실기동 테스트 결과

10개 동시 입찰 (모두 현재 ACTIVE 6000원을 outbid 시도):

| 입찰 | 금액 | 결과 |
|------|------|------|
| 1~4, 6~10 | 7100~8000 | BID_CONFLICT (409) |
| 5 | 7500 | ACTIVE (성공) |

```
성공: 1, 낙관적 락 충돌: 9, 기타: 0
```

DB 상태:
```
bid_id  amount   status   version
2       7500.00  ACTIVE   0
1       6000.00  OUTBID   1      ← version 증가 (1회 수정됨)
```

재시도(순차 입찰 9000원) → 정상 성공, ACTIVE 1개 유지.

## 5. 한계 — D7에서 분산 락이 필요한 이유

| 항목 | 낙관적 락 (D6) | 분산 락 (D7) |
|------|---------------|-------------|
| 충돌 시 | 실패 + 클라이언트 재시도 | 대기 후 진행 |
| 재시도 비율 | 동시성 높을수록 증가 | 0 (대기) |
| 직렬화 범위 | UPDATE만 (읽기 경합 가능) | 조회~저장 전체 |
| 구현 복잡도 | `@Version` 1줄 | Redis + Redisson |
| 분산 환경 | DB만으로 동작 | Redis 필요 |

동시 요청이 많을수록 실패율이 올라간다. 10개 동시 → 9개 실패(90%). 이건 실패 후 재시도 비용이 크다는 뜻이다. D7에서 Redisson 분산 락으로 "한 명씩 순서대로" 처리하게 바꾸면, 실패 대신 대기가 되므로 사용자 경험이 좋아진다.

## 면접에서 물어볼 만한 것

**Q: 낙관적 락 vs 비관적 락?**
- 낙관적: 읽을 때 락 안 걸고, 쓸 때 version 검사. 충돌이 드물 때 적합.
- 비관적: 읽을 때부터 `SELECT ... FOR UPDATE`로 행 잠금. 충돌이 잦을 때 적합하지만 데드락 위험.
- 경매 입찰처럼 같은 자원에 동시 쓰기가 잦으면, 낙관적은 재시도 지옥이 되고, 비관적은 DB 커넥션을 잡고 있어야 해서 스케일이 안 된다 → 분산 락이 답.

**Q: `@Version`은 어떤 SQL을 만드나?**
- `UPDATE ... SET version=version+1 WHERE id=? AND version=?`. 0 rows affected → Spring이 `ObjectOptimisticLockingFailureException`을 던진다. 이 예외는 `@Transactional` 프록시 밖에서 발생하므로, 서비스 메서드 내부 try-catch로 잡을 수 없다.

**Q: 이 구현에서 ACTIVE bid 2개가 생기는 시나리오가 완전히 사라지나?**
- 거의 사라지지만, 이론적으로는 첫 입찰(ACTIVE 없음)에서 2개의 INSERT가 동시에 일어나면 둘 다 성공할 수 있다 — INSERT에는 version 검사가 없기 때문. 이 케이스는 분산 락(D7)이나 DB UNIQUE 제약조건으로 막아야 한다.
