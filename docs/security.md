# 보안 정책

## 인증 흐름

1. 클라이언트가 JWT 토큰을 Authorization 헤더에 포함하여 요청
2. Gateway가 토큰을 검증 (서명, 만료)
3. 검증 성공 시 토큰에서 userId를 추출하여 X-User-Id 헤더로 내부 서비스에 전달
4. 검증 실패 시 401 응답

실패 경로: 토큰 없음 → 401, 토큰 만료 → 401, 서명 불일치 → 401.

## 인가

| 동작 | 조건 |
|------|------|
| 상품 등록 | 인증된 사용자 |
| 경매 시작 | 해당 상품의 판매자(sellerId == userId) |
| 입찰 | 인증된 사용자 AND sellerId != bidderId |
| 경매 조회 | 인증 불필요 (공개) |

본인 경매 입찰은 명시적으로 거부된다. 별도 관리자 역할은 없다.

## 서비스 간 통신

서비스 간 내부 통신(REST/gRPC, Kafka)에는 별도 인증을 적용하지 않는다 (학습 프로젝트 범위). 프로덕션에서는 mTLS 또는 서비스 메시로 보호해야 한다.

## 민감 데이터

- DB 비밀번호는 로컬에서는 docker-compose.yml 환경 변수, GKE에서는 K8s Secret으로 관리.
- JWT 서명 키는 환경 변수로 주입. 코드에 하드코딩하지 않는다.
