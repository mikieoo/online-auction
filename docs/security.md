# 보안 정책

## 인증 흐름

1. 클라이언트가 JWT 토큰을 Authorization 헤더에 포함하여 요청
2. Gateway가 토큰을 검증 (서명, 만료)
3. 검증 성공 시 토큰에서 userId를 추출하여 X-User-Id 헤더로 내부 서비스에 전달
4. 검증 실패 시 401 응답

실패 경로: 토큰 없음 → 401, 토큰 만료 → 401, 서명 불일치 → 401.

현재 상태(Gateway 구현 전, D4까지): 클라이언트가 각 서비스에 직접 `X-User-Id`를 넣어 호출한다. 서비스는 헤더 값을 그대로 신뢰하며, 헤더가 없으면 400으로 거절한다. 이 신뢰는 Gateway 뒤에 서비스가 놓인다는 전제이고, 서비스 포트가 외부에 직접 노출되면 인증이 없는 것과 같다.

## 인가

| 동작 | 조건 |
|------|------|
| 상품 등록 | 인증된 사용자 |
| 경매 생성 | 해당 상품의 판매자(sellerId == userId). 아니면 403 |
| 경매 시작 | 해당 상품의 판매자(sellerId == userId). 아니면 403 |
| 입찰 | 인증된 사용자 AND sellerId != bidderId. 판매자 본인이면 403 |
| 상품·경매·입찰 조회 | 인증 불필요 (공개). 경매 응답에는 sellerId·startingPrice가 포함된다 |
| 결제 조회 | 결제한 본인(payerId == userId). 아니면 403 |
| 낙찰 확정, 결제 생성 | 내부 API(`/internal/v1/**`). 사용자 인증 없음. Gateway가 라우팅하지 않는다 |

본인 경매 입찰은 명시적으로 거부된다. 별도 관리자 역할은 없다.

## 서비스 간 통신

서비스 간 내부 통신(REST/gRPC, Kafka)에는 별도 인증을 적용하지 않는다 (학습 프로젝트 범위). 내부 API는 `/internal/v1/` 경로로 분리해 Gateway가 외부에 노출하지 않는 것이 유일한 보호다. 프로덕션에서는 mTLS 또는 서비스 메시로 보호해야 한다.

## 민감 데이터

- DB 비밀번호는 로컬에서는 docker-compose.yml 환경 변수, GKE에서는 K8s Secret으로 관리.
- JWT 서명 키는 환경 변수로 주입. 코드에 하드코딩하지 않는다.
- 결제 정보(payerId, 금액, 결과)는 본인 외에 조회할 수 없다. 오류 메시지에도 타인의 결제 내용을 담지 않는다.
