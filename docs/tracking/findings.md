# 미해결 문제

## Bid 상태 전이 규칙과 차순위 승계의 모순

- **증상**: "한 경매에 ACTIVE Bid는 최대 1개, 새 입찰이 들어오면 이전 ACTIVE는 OUTBID"(D3 구현)와 "OUTBID → WINNER 전이 불가"(도메인 규칙)를 합치면, 결제 실패 후 다음 최고 입찰자(OUTBID 상태)를 WINNER로 만드는 차순위 승계(D10)가 규칙상 불가능하다.
- **영향**: D10 구현 시 도메인 규칙 문서와 코드(`Bid.markWinner()`는 ACTIVE에서만 허용) 중 하나를 바꿔야 한다. 지금은 승계 로직이 없어 런타임 영향은 없다.
- **왜 지금 해결하지 않나**: 차순위 승계는 D10 범위이고, 해법(OUTBID → WINNER를 허용할지, 승계 전용 상태를 둘지, "차순위"를 Bid 상태가 아닌 금액 순위로만 정의할지)은 D10 설계에서 사용자가 결정해야 한다.
- **가능한 접근**: D10에서 `OUTBID → WINNER`를 "이전 WINNER가 결제 실패로 OUTBID된 뒤"라는 조건부 전이로 허용하고, 다음 최고 입찰자는 "WINNER가 아니고 결제 실패 이력이 없는 입찰자 중 최고 금액"으로 정의한다.

## 동시 입찰로 ACTIVE Bid가 2개 생기면 그 경매의 입찰·정산이 전부 멈춘다

- **증상**: 락이 없는 D3에서 같은 경매에 동시 입찰이 들어와 ACTIVE Bid가 2개 저장되면, 이후 `findByAuctionIdAndStatus(auctionId, ACTIVE)`(Optional 반환)가 결과 2건으로 `IncorrectResultSizeDataAccessException`을 던진다. 그 경매의 모든 입찰 요청은 500, 낙찰 확정도 500이 되어 정산 스케줄러는 `CLOSED + winner_id NULL` 상태를 매 주기 재시도한다(영구 재시도).
- **영향**: 해당 경매 1건이 영구 정지. 다른 경매에는 영향 없음(경매별 try/catch). 부하 테스트(D6) 전에는 재현 확률이 낮다.
- **왜 지금 해결하지 않나**: 근본 원인(동시 입찰 직렬화)이 D6 낙관적 락·D7 분산 락의 주제다.
- **임시 복구**: `UPDATE bid SET status='OUTBID' WHERE bid_id = <금액이 낮은 쪽>`으로 ACTIVE를 1개로 만들면 다음 주기에 정산이 이어진다.
- **가능한 접근**: D7에서 락 도입 + `(auction_id, status)`에 ACTIVE 유일성을 보장하는 보조 장치(예: `active_flag` 컬럼 + UNIQUE) 검토.
- **현재(D20)**: D7 분산 락 + D20 재구성(락 안에 원격 호출 없음)으로, 남은 경로는 Redis 장애로 락이 무력화된 상태에서 첫 입찰 두 건이 동시에 INSERT되는 경우뿐이다(`@Version`은 INSERT를 막지 못한다). D19까지는 auction-service가 느릴 때 락 임대 시간(5초)이 처리 도중 만료되는 경로도 있었다. 근본 방어는 DB 제약이다: 생성 컬럼 `active_auction_id = IF(status='ACTIVE', auction_id, NULL)` + UNIQUE(NULL은 중복 허용이라 ACTIVE 행끼리만 충돌).

## 정산 대상 정렬이 auction_id 오름차순 고정이라 영구 실패 건이 뒤 경매를 굶길 수 있다

- **증상**: 정산 B단계는 `CLOSED + winner_id NULL` 경매를 auction_id 오름차순으로 틱당 50건만 집는다. 특정 경매들이 매번 실패(위 항목, 또는 bid-service가 특정 id에만 5xx)하면 그 50건이 매 주기 상한을 차지해 그 뒤의 새 경매는 정산되지 않는다.
- **영향**: 실패 건이 50건 미만이면 문제 없다. 50건 이상 누적되면 신규 경매 정산 지연이 무한정 늘어난다.
- **왜 지금 해결하지 않나**: D9에서 정산이 이벤트 기반으로 재설계되면 이 폴링 루프 자체가 사라진다.
- **가능한 접근**: 실패 횟수를 기록해 N회 초과 건은 뒤로 미루기, 또는 `updated_at` 오름차순 정렬.

## 스케줄러가 알 수 없는 결제 상태 문자열을 받으면 그 경매는 매 틱 재시도된다

- **증상**: payment-service가 `REQUESTED/COMPLETED/FAILED` 외의 status를 돌려주면 auction-service의 Feign 역직렬화가 실패해 그 틱은 건너뛰고, 다음 틱에 같은 경매를 다시 시도한다. 상태 집합이 바뀌지 않는 한 발생하지 않는다.
- **영향**: 상태 집합을 확장하는 배포 순서가 잘못되면 해당 경매의 정산이 멈추고 WARN 로그가 5초마다 남는다.
- **왜 지금 해결하지 않나**: D9에서 이 동기 호출 자체가 Kafka 이벤트로 대체된다. 그때 이벤트 스키마 호환 정책과 함께 다룬다.
- **가능한 접근**: 역직렬화 실패를 별도 카운트하고 N회 초과 시 findings/알람으로 승격.

## local 프로필이 아닌 환경에서 토큰을 발급할 수단이 없다

- **증상**: 토큰 발급 API(`POST /auth/token`)는 `local` 프로필에서만 존재한다. GKE 배포(D18)나 장애 시연(D28)처럼 `local`이 아닌 환경에서는 유효한 JWT를 얻을 방법이 없어, 인증이 필요한 모든 요청(쓰기, 결제 조회)을 Gateway로 보낼 수 없다.
- **영향**: D18 이후 Gateway 경유 쓰기 요청 전부. 부하 테스트(k6)도 같은 문제를 겪는다.
- **왜 지금 해결하지 않나**: 발급 방식(데모 전용 프로필을 GKE에서도 켤지, 사전 발급한 장기 토큰을 쓸지, 최소한의 로그인 서비스를 둘지)은 보안 수준과 포트폴리오 범위에 대한 사용자 결정이 필요하다.
- **가능한 접근**: (a) 서명 키를 아는 운영자가 로컬 스크립트로 토큰을 만들어 주입, (b) 별도 프로필(예: `demo`)에 발급 API를 열되 고정된 시연용 userId 집합만 허용, (c) 간단한 로그인 서비스 추가.

## 같은 상품의 WAITING 경매 둘을 동시에 시작하면 ACTIVE가 2개 된다

- **증상**: `AuctionService.ensureNoActiveAuction`은 "이 상품에 ACTIVE 경매가 있나"를 조회만 하고 락 없이 통과시킨다. 경매 생성은 ACTIVE만 검사하므로 같은 상품의 WAITING 경매가 여럿 생길 수 있고, 그 둘의 시작 요청이 동시에 오면 둘 다 "없음"을 보고 ACTIVE가 된다. `@Version`은 서로 다른 행이라 막지 못한다.
- **영향**: "상품당 ACTIVE 1개" 불변 조건 위반 → 같은 상품이 두 번 낙찰될 수 있다. 판매자 본인이 동시에 두 번 시작해야 하므로 빈도는 낮다.
- **왜 지금 해결하지 않나**: D20 범위(부하 테스트) 밖이고 스키마 변경이 따른다. 해법 선택을 사용자가 정해야 한다.
- **가능한 접근**: (1) 시작 시 product 행 `SELECT ... FOR UPDATE`로 같은 상품의 시작을 직렬화, (2) 생성 컬럼 `active_product_id = IF(status='ACTIVE', product_id, NULL)` + UNIQUE로 DB가 막게 한다. (2)는 검사를 빠뜨린 코드 경로도 막는다.

## 차순위 승계가 결제에 실패한 입찰자의 다른 입찰을 다시 고를 수 있다

- **증상**: `BidService.reassignWinner`는 "OUTBID 중 최고 금액"을 다음 낙찰자로 고르고, 결제에 실패한 입찰자를 제외하지 않는다. 같은 사람이 10,000원 → 12,000원으로 금액을 올렸다면(10,000원 입찰은 OUTBID), 12,000원 결제가 실패했을 때 같은 사람의 10,000원 입찰이 차순위로 뽑힌다.
- **영향**: 결제 실패한 사람에게 다시 결제가 요청되고, 승계 횟수(최대 3회) 1회가 낭비된다. 다른 입찰자는 그만큼 기회를 잃는다.
- **왜 지금 해결하지 않나**: 업무 규칙 결정이 필요하다 — 결제 실패한 입찰자의 다른 입찰도 전부 제외할지.
- **가능한 접근**: 제외한다면 `reassignWinner`에서 실격 시 같은 경매의 해당 입찰자 OUTBID 입찰을 함께 DISQUALIFIED로 바꾸거나, 차순위 조회에 `bidder_id != failedBidderId` 조건을 더한다.

## Outbox 발행기: 영구 실패 행 하나가 뒤의 모든 이벤트를 막는다

- **증상**: `OutboxPublisher`는 순서 보장을 위해 발행 실패 시 그 자리에서 멈추고(`break`) 다음 폴링에서 같은 행부터 다시 시도한다. 어떤 행이 영원히 실패하면(예: 이벤트 클래스 이름 변경으로 `Class.forName` 실패) 그 뒤의 이벤트가 전부 발행되지 않는다(head-of-line blocking). 또 발행기 전체가 `@Transactional`이라 Kafka 전송(건당 최대 5초 대기, 최대 100건)을 하는 동안 DB 커넥션을 붙잡는다 — 원격 호출을 트랜잭션 밖에 두는 원칙과 어긋난다.
- **영향**: 정상 운영에서는 발생하지 않는다. 배포 실수 하나로 해당 서비스의 모든 이벤트가 멈출 수 있고, Kafka가 느려지면 커넥션 점유와 ShedLock 만료(30초) 초과가 생길 수 있다(중복 발행은 멱등 컨슈머가 흡수).
- **왜 지금 해결하지 않나**: D20 범위 밖. 순서 보장 단위를 전역이 아니라 aggregate(경매) 단위로 바꾸는 설계 결정이 필요하다.
- **가능한 접근**: 행에 실패 횟수를 기록하고 N회 초과 행은 별도 상태로 빼기(같은 aggregate의 뒤 이벤트만 보류), 발행은 트랜잭션 밖에서 하고 `published` 표시만 짧은 트랜잭션으로.
